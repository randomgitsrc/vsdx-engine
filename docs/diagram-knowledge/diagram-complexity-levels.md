# 图形复杂度分级：Level 1–3 的校准

**状态：** Proposed（研究结论，待项目所有者确认）
**日期：** 2026-11-19
**依据 Goal：** `goal-2.1.md` §4.3、§4.4
**性质：** 对 Goal 提出的 Level 1–3 进行独立校准，**不是照搬**

---

## 一、校准结论摘要

Goal 2.1 §4.3 明确写了 Level 1–3 是「研究假设，不是行业标准」，并要求校准。本文件完成校准。

**核心发现：Goal 的 Level 分级把「元素类型丰富度」和「布局约束难度」混在同一维度上。**
这两个维度在真实案例中并不同步——一个只有矩形和箭头的图，可能因为约束密集而极难布局；
一个图标丰富的图，可能因为结构简单而容易。

**修正建议**：Level 应定义为**两个正交维度的组合**，而不是一个递增序列。

| 维度 | 含义 |
| --- | --- |
| **表达能力（Expressiveness）** | 需要哪些图形对象类型：容器、嵌套、多文本区、通条、图标、多种关系 |
| **布局难度（Constraint Difficulty）** | 在给定约束下求解合理布局的难度：对齐、等距、避障、跨区路由、密度上限 |

## 三、对 Goal Level 1–3 的具体校准

### 3.1 Level 1「标准专业分层架构」— 基本合理，但边界模糊

Goal 列举：4–5 层、每层多组件、层背景与标题、组件标题与说明、适量连接、跨层连接、合理尺寸与留白。

**校准意见**：

| 项 | 判断 | 理由 |
| --- | --- | --- |
| 4–5 层 | ⚠️ 应改为「由被描述系统决定」 | C4 明确分层是抽象的层次（system/container/component/code），不是固定 4–5；AWS 参考架构常见 3–6 层，无标准值 |
| 层背景+标题 | ✅ 保留 | 这是分层架构的识别特征 |
| 组件标题+说明 | ✅ 保留，但应升为 Level 1 的**硬要求** | C4 清单第一条就是"每个元素有名字、能理解它做什么" |
| 跨层连接 | ✅ 保留 | — |
| 「适量」层内连接 | ⚠️ 不可判定 | 应改为可测：**AWSLabs 的 13+ 服务需加大间距**是现成阈值 |

**建议的 Level 1 可判定验收**（替换主观描述）：

1. 每个元素有名称，且无缩写未解释（C4 清单）
2. 每条箭头有描述意图的标签（C4 清单）
3. 跨层连接不穿过无关组件（AWSLabs 边路由规则）
4. 同一服务的多条出边从不同侧面引出（AWSLabs）
5. 成品字号 ≥ 7 pt（Elsevier）

### 3.2 Level 2「复杂专业分层架构」— 需要拆维度

Goal 列举：嵌套组件、嵌套区域、横向通条、纵向贯穿区、多文本区、多视觉结构、图标、多对多跨层连接、复杂容器、局部约束、局部重布局。

**校准意见**：这 11 项里混了三类东西。

| Goal 原文项 | 实际维度 | 说明 |
| --- | --- | --- |
| 嵌套组件、嵌套区域、复杂容器 | **表达能力** | 模型能否表达父子关系 |
| 多文本区、多视觉结构、图标 | **表达能力** | 单个组件内部的丰富度 |
| 横向通条、纵向贯穿区 | **表达能力 + 布局** | 跨越多个容器，布局时必须协调 |
| 多对多跨层连接 | **布局难度** | 交叉最小化问题 |
| 局部约束、局部重布局 | **布局难度** | Hybrid 布局，与表达能力无关 |

**结论**：Level 2 不应是"Level 1 加更多元素"，而应是**两个维度各自升级**。

### 3.3 Level 3「综合专业架构」— 缺少明确的「不同」之处

Goal 列举：多区域嵌套、多种对象、图标设备矢量图、多种关系、复杂跨区域连接、多面板、局部细节图、大幅面、多页多图、更复杂约束。

**校准意见**：这些**大部分是 Level 2 的量的累加**，不是质的变化。真正属于 Level 3 的是两件：

1. **多页/多图组织**——需要跨页的对象身份与引用，这是模型层的新能力
2. **局部细节图 + 总览的对应关系**——需要"图上图"或缩放层级

其余（更大纸张、更多图标、更多连接）都是 Level 2 在更大规模上的重复。

**建议**：Level 3 的定义应聚焦「**一页装不下时如何组织**」，而不是「Level 2 但更多」。

## 四、修正后的分级定义（建议稿）

### 维度 A：表达能力（E1–E3）

| 级别 | 能力 |
| --- | --- |
| **E1** | 扁平容器 + 单一文本区 + 单一关系样式 |
| **E2** | 嵌套容器、多文本区（标题/说明/状态）、通条、多种关系语义 |
| **E3** | 图标/矢量对象作为组件主体、跨容器复合对象、图上图（细节嵌入） |

### 维度 B：布局难度（D1–D3）

| 级别 | 能力 |
| --- | --- |
| **D1** | 单层内排列，无跨容器路由 |
| **D2** | 多层对齐 + 跨层路由避障 + 多对多连接交叉控制 |
| **D3** | 全局约束求解（对齐/等距/密度上限同时满足）+ 局部重布局不破坏整体 |

### 这两个维度**不构成全序**

E 和 D 是正交的，不能互相补偿。因此不存在"Level 1 < Level 2 < Level 3"这样的线性排序，
只有**九种组合**（E1–E3 × D1–D3）。

**只给其中三档命名**，因为这三档对应真实的产品目标：

| 命名 | 组合 | 含义 | 对应 Goal |
| --- | --- | --- | --- |
| **Level 1** | E1 + D2 | 结构简单但布局要求高——常规分层架构的真实难度在这里 | Goal Level 1 |
| **Level 2** | E2 + D2 | 表达与布局同时提升 | Goal Level 2 |
| **Level 3** | E3 + D3 + 多页 | 图上图、多页组织 | Goal Level 3 |

**其余六格不命名**（E1+D1、E1+D3、E2+D1、E2+D3、E3+D1、E3+D2），
因为：

1. 它们是真实的组合（如 E1+D3 = 扁平但高密度的基准图），但没有对应的产品目标
2. 给它们编号会制造"等级"的错觉，而它们只是不同方向上的不同难度

**关键性质**：这三档**不可比**。E1+D2 与 E2+D1 谁"更高"没有意义——
一个表达弱但布局难，一个表达强但布局易。产品不会因为达到 E2+D1 就"接近 Level 2"。

**初稿的错误**：本节原先写「Level 2- = E2+D1」，暗示存在一个介于 Level 1 和 Level 2 之间的等级。
这是把正交维度当成线性序列，与本文件的整个论点矛盾。已删除。

## 五、与当前引擎的对照（事实基线）

**方法**：读源码 + 实测产物，不依据任何历史报告。

| 能力 | 状态 | 证据 |
| --- | --- | --- |
| 扁平容器（层） | ✅ 完整 | `examples/realworld/cbo.vsdx` 有 3 个 `msvStructureType=Container` |
| 层背景 + 标题 | ✅ 完整 | 同上，标题为独立文本块 |
| 组件标题 + 说明（两行） | ✅ 完整 | `Node.Text` 支持 `\n`；实测 `cbo` 的节点标签只有「API 网关」（**无 Kong**），Kong 出现在 `skill/SKILL.md` 与非 cbo 示例中 |
| 单一关系样式 | ✅ 完整 | `Edge.Kind` = straight/rightAngle/curved |
| 多种关系语义 | ⚠️ 部分 | `Relation` 支持 8 种语义，但只影响箭头有无与标签默认值，**不改变视觉样式** |
| 嵌套容器 | ⚠️ 部分 | `Group.ParentId` 存在，但 Visio 内为兄弟容器（见 `docs/limitations.md` §2 R7） |
| 多文本区（标题/说明/状态分区） | ❌ 未实现 | `Node` 只有单个 `Text` 字段 |
| 横向通条 | ❌ 未实现 | 无跨容器对象类型 |
| 图标/矢量作为组件主体 | ⚠️ 部分 | `FreePath` 可写自定义几何，但无图标库、无 SVG 导入 |
| 跨层路由避障 | ⚠️ 部分 | `OrthogonalRouter` 有避障，但只对穿过形状的直边生效 |
| 多对多交叉控制 | ❌ 未实现 | 无交叉最小化；`deploy-topology` 有 5 处交叉 |
| 全局约束求解 | ❌ 未实现 | 布局是推导式的，无约束求解器 |
| 多页组织 | ⚠️ 部分 | 模型支持多页，但无跨页引用 |

**结论（已按评审意见更正）**：当前引擎在表达维度约为 **E1.5**（有容器与多行文本，无分区样式与关系视觉），
在布局维度约为 **D1.5**（单层排列可靠，跨容器路由与交叉控制不足）。

**按本文件自己的组合表（§四）**：

| 等级 | 要求 | 当前 | 判定 |
| --- | --- | --- | --- |
| Level 1 | E1 + **D2** | E1.5 + D1.5 | ❌ **D 不达标** |
| Level 2 | **E2** + **D2** | E1.5 + D1.5 | ❌ 双重不达标 |
| Level 3 | E3 + D3 + 多页 | — | ❌ |

**初稿写「处于 Level 1 与 Level 2 之间」是错误的**——这个说法预设了单维度的线性排序，
而本文件的整个论点是**两个维度不能互相补偿**。E1.5 不能代替 D2，D1.5 也不能代替 E2。
「E1.5/D1.5」本身也不是定义好的等级，只是一个描述。

**准确的表述**：当前引擎**尚未达到任何一档**；它最接近 Level 1，差在布局维度（D2）。

**两处需要更正的初判**：

1. 初稿写「关系只有箭头有无」，实测 `Relation` 支持 8 种语义，只是不驱动视觉——
   性质不同（不是"没建模"，是"建模了但没表达"），结论不变。
2. 初稿的「Level 1 与 Level 2 之间」是错的，理由如上。

这与 `docs/phase8/status-2026-11.md` 的整体判断方向一致（该文件未使用"结构性图可用"这一措辞，**本句初稿误引**），但那份文件没有指出**具体卡在哪一维度**。

## 七、本文件的局限

1. **只有 4 个外部来源**，其中 2 个（C4、AWS）是软件架构领域，1 个（Elsevier）是学术出版，**没有覆盖企业 IT 架构实践**（如 TOGAF、ArchiMate）。
2. **没有真实 Visio 案例样本**——本机无 Visio，无法获取企业级 .vsdx 原件。
3. **E/D 双维度模型是本文件的推断**，不是既有理论。它比 Goal 的单维分级更能解释现状，但同样需要评审。

**这些局限不影响"Goal 的 Level 分级需要校准"这一结论**，但影响校准结果的确定性。
