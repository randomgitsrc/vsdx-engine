# 输出适配与物理可读性

**状态：** Proposed
**日期：** 2026-11-19
**依据 Goal：** `goal-2.1.md` §6.1–§6.4
**目的：** 回答「A4/A3/Web 输出下，什么字号和密度是专业可读的」

---

## 一、核心结论

**Goal §6.2 的论点是正确的，且可以量化。**

> 「原图 30cm 缩到 18cm，9pt 正文最终只有约 5.4pt」——这个换算成立，但它**只是问题的一半**。

完整的关系是三个变量：

```
成品字号(pt) = 设计字号(pt) × (目标页面宽度 / 内容宽度)
```

**关键推论：字号不是排版参数，而是输出的约束条件。**

如果要求成品 ≥ 7 pt，那么：

```
内容宽度上限 = 目标页面宽度 × (设计字号 / 7)
```

一张 A4 横向（29.7cm 宽，含边距可用约 27cm）的图，若组件正文设计为 10 pt，则内容宽度不得超过
`27 × 10/7 ≈ 38.6cm`。**超过就必须换纸或拆图，而不是缩小。**

## 二、证据

### 2.1 物理可读性下限

| 来源 | 数值 | 原文 |
| --- | --- | --- |
| [Elsevier 制图规范](https://www.elsevier.com/en-gb/about/policies-and-standards/author/artwork-and-media-instructions/artwork-sizing) | 正文 **7 pt**，上下标不低于 **6 pt** | "lettering on the artwork should have a finished, printed size of 7 pt for normal text and no smaller than 6 pt for subscript and superscript" |
| 同上 | 更小则「几乎无法辨读」 | "Smaller lettering will yield text that is hardly legible" |
| 同上 |  tints/shading 可能要求 10 pt | "instances where other factors in the artwork (e.g., tints and shadings) dictate a finished size of perhaps 10 pt" |

**这是学术出版方的经验法则**（原文自称 rule-of-thumb），不是 ISO 标准。但它给出了一个**有出处的、可引用的下界**。

### 2.2 与当前引擎的关系

当前引擎的 `MinReadablePt = 8.0`（`TypeScale`），**高于 Elsevier 的 7 pt**。这个值是合理的保守选择。

但引擎**没有检查成品字号**——它检查的是模型里的字号是否低于 8 pt，而不是**在目标纸张上实际呈现多大**。

### 2.3 间距与密度的量化阈值

| 来源 | 规则 |
| --- | --- |
| [AWS 布局指南](https://raw.githubusercontent.com/awslabs/agent-plugins/main/plugins/deploy-on-aws/skills/aws-architecture-diagram/references/layout-guidelines.md) | 120px 服务容器之间：水平 180px / 垂直 120px |
| 同上 | 13+ 服务：水平 220px / 垂直 160px |
| 同上 | 箭头端点与标签文字保持 30px 净距 |
| 同上 | 每张图决策点最多 1–2 个 |

AWS 的像素值对应其图标尺寸（78px / 48px），不能直接换算成英寸。**可借鉴的是比例**：
服务间距约为图标尺寸的 1.5–2.3 倍。

## 三、输出规格（Output Profile）建议

Goal §6.1 要求建立 Output Profile 机制。基于上述证据，建议每个 profile 至少定义：

| 字段 | 含义 | A4 横向示例 |
| --- | --- | --- |
| `page.width` / `page.height` | 物理尺寸 | 297 × 210 mm |
| `page.margin` | 页边距 | 15 mm（四边） |
| `readable.minTextPt` | 成品最小正文字号 | 7 pt（Elsevier 下界） |
| `readable.preferredTextPt` | 建议正文字号 | 9 pt |
| `readable.minLabelPt` | 连线标签最小 | 7 pt |
| `density.maxComponents` | 单页合理组件数 | 见下文 |
| `density.minGapMm` | 组件最小净距 | 5 mm（约 14 pt） |

### 3.1 判据不是密度，是缩放后的可读性

**先说清楚一个曾经写错的地方。**

本文件初稿提出「单页组件数 ≤12 舒适 / 13–20 临界 / >20 超限」。
**这个判据是错的**，原因：

> 一张 40 个组件的图，如果缩放到 A4 后字号仍有 8 pt、布局仍合理，**它就是好图**。

复杂度本身不是缺陷。把密度做成独立门槛，会把专业图里正常存在的高密度图判成不合格。

**正确的判据只有一个：缩放后，内容在目标纸张上的实际呈现是否可读、布局是否合理。**

密度只是**影响**结果的一个因素，不是结果本身。

### 3.2 容量应由字号约束**反推**，而不是拍一个密度上限

给定「正文 9 pt，成品不得低于 7 pt」，可接受的极限缩放是 `7/9 = 78%`。

反过来，内容尺寸上限就是「纸张可用尺寸 ÷ 78%」：

| 纸张 | 可用尺寸 | 内容上限（78% 缩放）| 可放组件（组件 2.8×1.2" + 间距 0.8×1.0"）|
| --- | --- | --- | --- |
| A4 横向 | 10.7 × 7.3" | 13.7 × 9.4" | **3 列 × 4 行 = 12** |
| A3 横向 | 15.9 × 10.7" | 20.4 × 13.7" | **5 列 × 6 行 = 30** |

**这张表才是「能放多少」的正确来源**——它由字号下限推出来，不是估的。

**但它仍然不是判据。** 它只说明「在 9 pt 正文、组件尺寸固定的前提下，A4 大约能放 12 个」。
如果组件更小（2.0×0.9"），A4 能放更多；如果正文用 10 pt，能放的更少。

**判据始终是 §3.1 那条**：缩放后成品字号 ≥ 7 pt 且布局合理。

### 3.3 因此需要的计算

```
缩放比   = 目标纸张可用宽度 / 内容宽度
成品字号 = 设计字号 × 缩放比
```

判据：

- `成品字号 ≥ readable.minTextPt`（正文 7 pt，见 §二）
- 布局在缩放后仍合理（间距、对齐关系按比例保持）
- **两条都满足 → 图可用，无论有多少组件**

### 3.4 当前引擎缺的正是这一步

**实测结论**（`src/Vsdx.Protocol/DesignSpec.cs` 关于 `shrinkToFit` 的注释）：

> "Nothing shrinks the drawing"

引擎的 `shrinkToFit` 做的是**放大页面去容纳内容**（`DiagramSizer.FitPage` 把页面设成内容包围盒），
**不是缩小图形去适配指定纸张**。

所以现在的行为是二选一：

| 情况 | 引擎行为 |
| --- | --- |
| 内容超出指定纸张 | 报 `node.out-of-page`，`hardConstraintsPassed: false` |
| 不指定纸张 | 页面自动长成内容那么大（可能是 A2 甚至更大）|

**缺的是第三条路**：内容不变，等比缩放到目标纸张，然后检查成品字号。

### 3.5 这条路的可行性

数学上没有障碍——缩放是线性变换。需要确认的是：

| 待确认 | 为什么重要 |
| --- | --- |
| Visio 是否有「页面缩放」或「打印缩放」概念 | 若 Visio 原生支持，应写入该字段而不是改所有形状坐标 |
| 缩放后线宽是否等比 | 1 pt 线缩到 0.6 会变细，可能需设下限 |
| 缩放后字号是否真的按比例 | 需 L4 验证 Visio 的打印行为 |

**前两项可通过读 Visio 规范确认，第三项 Blocked（无 Visio）。**

## 四、Web / Screen 输出（**非当前优先目标**）

**项目所有者已裁定：Web 不是优先目标，先把纸张做好。**

因此本文件不对 Web 输出定义验收标准，也不做密度建议。
先前版本给出的「≤30 组件」是**无来源的推断**，已删除。

**若将来要做**，需要先回答（这些目前都没有答案）：

| 问题 | 为什么不能照搬纸张的判据 |
| --- | --- |
| 视口宽度不固定 | 纸张判据依赖「目标页面宽度」，Web 没有唯一值 |
| 字号由 CSS px 决定 | 与 pt 的换算依赖设备 DPI，"7 pt" 无对应物 |
| 可滚动、可缩放 | 「是否溢出」「页面利用率」在 Web 上不成立 |
| 阅读疲劳 | 纸张的密度上限来自页面积，Web 的来自滚动距离——不同机制 |

**结论**：Web 输出属于产品范围决策（Goal §11.3 C 类），在所有者明确要求前不投入。

## 五、当前引擎的实际表现（事实基线）

**方法**：实测六个真实场景在 `canvas.mode=paper` 下的行为。

| 场景 | 落在哪张纸 | 内容宽度 | 是否检查成品字号 |
| --- | --- | --- | --- |
| `cbo` | A4 纵向 11.69×16.54" | — | ❌ 未检查 |
| `deploy-topology` | A4 横向 11.69×8.27" | — | ❌ |
| `user-data-flow` | A3 横向 16.54×11.69" | — | ❌ |

**关键缺口**：引擎选择纸张时**只看内容包围盒是否能装下**，不检查缩放后的字号是否仍可读。

这与 Goal §6.2 的警告直接冲突：

> 「文件可能合法，页面也没有溢出，但已经不适合正常阅读。」

### 5.1 一个具体的反例（已按实测更正）

`user-data-flow` 的节点包围盒实测 **13.93"** 宽（不是 16.54"——那是它自己选中的 A3 页宽）。

若强制放在 A4 横向（可用约 10.6"），需要缩小到 `10.6/13.93 ≈ 76%`。
若原设计正文为 9 pt，成品约 **6.9 pt** —— **低于 Elsevier 的 7 pt 正文下限**。

**当前引擎的行为（实测更正）**：它**会拦截**，但拦的是「形状出界」而不是「字号不可读」：

| 实测项 | 值 |
| --- | --- |
| `status` | `partial` |
| `hardConstraintsPassed` | **`false`** |
| `score` | **0** |
| `issueCodes` | `node.out-of-page` |

**这不是「不阻止」，而是「以错误的理由阻止」**：
调用方看到的是"形状超出页面"，而不是"字号会小到读不清"。
两者都导致失败，但如果调用方按提示把内容压进页面（而不是换纸），
**字号问题依然存在且不会被发现**。

**初稿的错误**：本文件此前写「当前引擎不会阻止这个操作，也不会警告」，
与产物矛盾。已按实测更正。

## 六、建议的最小实现

按 Goal「先研究后实施」的要求，这里只提方案，不实施：

1. **Output Profile 作为 DesignSpec 的一部分**（`canvas.profile: "a4-landscape"` 等）
2. **适配时计算成品字号**：`成品pt = 设计pt × 缩放比`
3. **低于 `readable.minTextPt` 时**：
   - 若是 `mode=paper` 且允许换纸 → 升到更大纸张
   - 否则报告 `output.text-too-small`，并给出建议纸张
4. **不得静默缩小**——这是 Goal §5.3 与项目既有铁律的共同要求

## 七、本文件的局限

1. **7 pt 来自单一来源**（Elsevier），且原文自称 rule-of-thumb。没有找到 ISO/ANSI 的对应规定。
2. **密度阈值（12/20）是从 AWS 的像素比例反推**，未在真实专业图上验证。
3. **Web 输出无权威来源**，「≤ 30」是推断。
4. **没有实测**：本机无 Visio，无法确认真实 Visio 文件的字号在打印时的实际表现。

**结论的确定性**：`成品字号 = 设计字号 × 缩放比` 是**数学恒等式**，不受上述局限影响。
有争议的只是阈值取值。
