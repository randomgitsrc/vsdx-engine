# 专业架构图：领域知识基线

**状态：** Proposed
**日期：** 2026-11-19
**目的：** 让未参与此前讨论的 Agent 理解「专业架构图」在本项目中指什么
**依据 Goal：** §4.2（专业架构图的含义）、§4.6（不要等同于 Mermaid）

---

## 一、本项目说的「专业架构图」是什么

**不是**：若干矩形框、几层水平色带、节点加箭头、一个 Mermaid 输出。

**是**：专业架构师在 Visio / draw.io 中构建的技术与业务架构图，具有：

- 可辨识的**层次结构**（不只是排版，而是语义分层）
- 组件内部有**信息分工**（标题 / 说明 / 状态）
- 跨层的**公共能力**（通条）
- 表达**不同关系类型**的连线（不只是同一种箭头）
- 通过图标/矢量对象传达**设备或系统类型**
- 整体上让读者能在 30 秒内理解系统的组成与关键交互

---

## 二、七种构成要素

Goal §4.2 定义了七类，以下是**用可判定语言重述**（因为原文描述偏抽象）：

### A. 层（Layer）

逻辑/技术/架构层次。**判定标准**：层有名称、有背景区分、层内组件属于该层。

**注意**：具体层数由被描述的系统决定。**不存在"标准 4–5 层"**——
C4 模型的分层是抽象层次（system/container/component/code），不是层数。

### B. 区域（Zone）

业务区域、系统边界、网络域、安全域、部署区域。可以嵌套。

**与层的区别**：层强调**纵向的抽象级别**，区域强调**横向的归属边界**。
一张图可以同时有层和区域（如"安全域"横跨多个层）。

### C. 组件（Component）

系统/服务/模块/平台/设备/业务能力。

**不应只是矩形加文本。** 需要研究的信息分工：

| 区域 | 作用 |
| --- | --- |
| 标题区 | 组件名 |
| 说明区 | 技术栈、职责 |
| 状态区 | 实例数、健康状态 |
| 标题条 | 顶部色条，表示类型 |
| 边框/背景 | 类型区分 |

**当前引擎只支持单一 `Text` 字段**（可用 `\n` 分行），无分区能力。

### D. 通条（Band）

横向共享服务条、纵向贯穿能力、跨区域统一管理。

**判定标准**：它同时属于多个层/区域，而不是恰好盖住它们的范围。

**实验 E1 结论**：当前引擎只能做**视觉近似**（一个跨越多层的高矩形，`groupId=null`），
无跨层语义。详见 `docs/research/experiments/E1-band-expression.md`。

### E. 图标与图形对象

云、数据库、服务器、网络设备、存储、安全设备、自定义 SVG。

**关键判断**：图标应是**组件的主体视觉对象**，而不只是文字前的装饰。

**当前状态**：`FreePath` 可写自定义几何，但**无图标库、无 SVG 导入**。

### F. 连接与关系

单向、双向、数据流、控制流、依赖、物理连接、跨层、跨区域、多对多、
端口、标签、复杂正交布线。

**必须区分关系类型**——不同关系不应全部用同一种箭头。

**当前状态（实测修正）**：`Edge.Relation` **支持 8 种语义**——
`calls | reads | writes | publishes | consumes | depends | contains | flows`。

但它只驱动两件事：

1. **箭头有无**（`RelationUsesArrow`：`contains` 不带箭头）
2. **标签默认值**（未给 `Label` 时回落为 `Relation`）

**不驱动线型、颜色或视觉样式**——注释写 "Drives line style and arrow defaults"，
但代码只实现了箭头部分。因此「不同关系用不同视觉」**当前不成立**。

### G. 整体视觉组织

信息层次、阅读路径、构图、视觉平衡、页面比例、颜色、字体、字号、
元素大小、间距、留白、内容密度、一致性。

## 三、如何判断一张图是否「专业」——可判定清单

**来源**：[C4 model 官方评审清单](https://c4model.com/diagrams/checklist)（CC BY 4.0）

这些是**是非题**，不是主观感受：

### 整体

- [ ] 图有标题
- [ ] 能看懂这是什么类型的图
- [ ] 能看懂图的范围（scope）
- [ ] 有图例/键

### 元素

- [ ] 每个元素有名称
- [ ] 能看懂每个元素的**类型**（抽象级别）
- [ ] 能看懂每个元素**做什么**
- [ ] 适用时，能看懂每个元素的**技术选型**
- [ ] 所有缩写/简称有解释
- [ ] 所有**颜色**的含义可理解
- [ ] 所有**形状**的含义可理解
- [ ] 所有**图标**的含义可理解
- [ ] 所有**边框样式**（实线/虚线）的含义可理解
- [ ] 所有**元素大小**的含义可理解

### 关系

- [ ] **每条箭头有描述意图的标签**
- [ ] 描述与箭头方向一致
- [ ] 适用时，能看懂关系上的技术选型（如协议）
- [ ] 所有缩写有解释
- [ ] 所有颜色的含义可理解
- [ ] 所有**箭头形状**的含义可理解
- [ ] 所有**线型**（实线/虚线）的含义可理解

**这份清单的价值**：它把「专业」从主观判断变成可逐条检查的问题。
**当前引擎只能自动检查其中 0 项**——这些都需要语义理解，属 Figure-Agent 职责。

## 四、布局的量化要求

**来源**：[AWS 官方布局指南](https://raw.githubusercontent.com/awslabs/agent-plugins/main/plugins/deploy-on-aws/skills/aws-architecture-diagram/references/layout-guidelines.md)

AWS 的像素值对应其图标尺寸（78px / 48px），**不能直接换算成英寸**。可借鉴的是**比例**：

| 规则 | AWS 数值 | 可借鉴的比例 |
| --- | --- | --- |
| 服务容器间距 | 水平 180px / 垂直 120px | 约图标尺寸的 2.3× / 1.5× |
| 13+ 服务时 | 水平 220px / 垂直 160px | 加大约 25% |
| 箭头端点与文字 | 30px 净距 | 约图标尺寸的 0.4× |
| 决策点数量 | 每图 1–2 个 | 密度上限信号 |

**另外两条强要求**：

1. 一个服务的多条出边**必须从不同侧面引出**——否则读者无法追踪
2. 非相邻连接**必须绕开中间容器**——直穿会被读成"穿过"而非"跳过"

## 五、当前引擎的能力对照

| 要素 | 状态 | 证据 |
| --- | --- | --- |
| A 层 | ✅ 完整 | 容器 + 标题 + 背景 |
| B 区域 | ⚠️ 部分 | 容器可嵌套，但 Visio 内为兄弟 |
| C 组件（多信息区） | ❌ 未实现 | 只有单一 `Text` |
| D 通条（跨层语义） | ❌ 未实现 | E1 实验：只能视觉近似 |
| E 图标 | ⚠️ 部分 | `FreePath` 可写几何，无图标库 |
| F 关系类型 | ⚠️ 部分 | 只有箭头有无，无数据流/控制流 |
| G 视觉组织 | ⚠️ 部分 | 有配色/字号层级，无构图决策 |

**结论**：当前处于「**能画出结构正确的分层图，但组件内部贫乏、关系无类型、通条无语义**」。

## 六、明确不要做的

Goal §4.6 要求：

> 语法支持不等于专业视觉表达能力。

- **不**追求 Mermaid / PlantUML 的语法覆盖
- **不**把"能生成 ASCII 图或 Mermaid 代码"等同于专业制图
- **不**以图形种类数量为目标（Goal §3.1）

可以研究互操作与导入，但**不以复制某种 DSL 为目标**。

## 附：形状的视觉权重（实测约束）

**为什么这条重要**：C4 把客户端和外部系统称为**支撑元素**（supporting elements），把范围内的容器称为**主要元素**（primary elements）。视觉权重应当同向——支撑元素不该压过主要元素。

**当前引擎的实测结果与此相反**：

| 角色 | 形状 | 实测尺寸 | 面积 |
| --- | --- | --- | --- |
| `client` | Circle | 1.85 × 1.85" | **3.42 in²** |
| `service` | Rectangle | 1.30 × 0.55" | 0.72 in² |

**圆形的面积是矩形的 4.8 倍。** 这不是参数没调好，是几何必然：

```
圆内能放下的矩形 = 的 0.70 × 直径（InscribedFactor）
要放 1.40" 宽的文字 -> 直径必须 ≥ 1.40 / 0.70 = 2.00"
矩形只需高度容下文字（0.55"），宽度可以自由伸展
```

**结论：圆形不适合承载长标签。** 任何"把圆缩小"的做法都会切字。

### 可选的处置（按代价排序）

| 方案 | 代价 | 后果 |
| --- | --- | --- |
| 缩短客户端标签（`Web` 而非 `Web 商城`）| 低，调用方责任 | 直径从 2.00 降到 1.30（受 `MinNodeWidth` 兜底）|
| 把 `client` 映射为矩形 | 中，改协议 | 与 C4 惯例不同，但视觉层级正确 |
| 缩小圆内字号 | 中，需按形状分字号 | 可读性下降，与 8pt 地板冲突 |

**未做决策**：这条需要所有者定，因为它改变所有含客户端的图。

**验证方法**：`grep -n "client" src/Vsdx.Protocol/DiagramIr.cs` 看当前映射；
`export-model` 后比对各角色节点的 `w*h`。

### 连接点：写入了，但预览不认

**实测（2026-11-19）**：所有形状现在有 4 个连接点（四边中点），已进入 VSDX 的
`Connection` 段。但**渲染出的 PNG 逐字节相同**，连线的落点没有任何变化。

原因是渲染走 OfficeIMO 的 `page.SaveAsImage()`，它自己计算连线路径，**不读连接点**。

| 环节 | 是否使用连接点 |
| --- | --- |
| 写入 VSDX | ✅ 是（4 个，四边中点）|
| **本项目 PNG 预览** | ❌ **否**——布局器的走线结果直接决定落点 |
| Visio 原生打开 | **未知**（L4 Blocked）|

**这意味着**：连接点修复解决的是「Visio 里连线该从哪进」，不是「预览里的线结」。
预览里的线结仍由路由器的端口选择决定，与连接点无关。

**要在预览里消除线结**，得改 `OrthogonalRouter` 的端口分配：同一节点收到多条线时，
分散到不同的边，而不是全从 `left` 出。

**验证方法**：
```bash
grep -c 'Row T="Connection"' <解压后的 page1.xml>   # 应为每形状 4
```
再对比渲染 PNG 的哈希——**相同就说明预览不认连接点**。

## 附：容器并排（2026-11-20 新增）

**背景**：引擎此前**无法表达「容器并排」**。`layered` 把每个容器当成一个带，按位置上下堆叠；
六种策略里 `Grid` 遇到容器直接退化为 `layered`，`Swimlane` 排的是泳道**内部**的流程。

**代价**：蜂窝架构、多区域部署、任何「N 个平行单元」的图都被画成竖排列表。
`slack-cellular` 案例暴露了它——三个 AZ 应该并排，实际竖排且连线绕出页面右侧。

### 用法

**给同层的容器相同的 `order`**：

```jsonc
"containers": [
  { "id": "az-a", "label": "us-east-1a", "order": 1 },
  { "id": "az-b", "label": "us-east-1b", "order": 1 },
  { "id": "az-c", "label": "us-east-1c", "order": 1 }
]
```

- **order 相同** → 同层 → **并排**
- **order 不同** → 不同层 → 竖排（原有行为）
- **不写 order** → 每容器一层 → 竖排（向后兼容）

### 两条实现约束

1. **同层成员按容器分组排列**，组间加间隙。否则各容器的包围盒会横跨整行——
   实测过 `az-a` 宽 10.78 英寸而它的成员只占约 4。
2. **`EvenBands` 按行生效**：单容器行仍对齐到**全页**宽度（`cbo` 三层等宽），
   多容器行保留各自列位置（否则三个容器叠在同一处）。

### 验证方式

```
grep -n "ContainersSharingALayerSitSideBySide" tests/Vsdx.Tests/SideBySideContainersTests.cs
```

以及 `examples/realworld/slack-cellular.ir.json` 的渲染结果。
