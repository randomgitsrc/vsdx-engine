# 第五轮真实场景验证：时序图（2026-11-18，HEAD `618de97`）

## 一、场景

前四种结构分别是：分层容器（架构、部署）、无容器长链（数据流）、有环状态机。
这一轮测**时序图**：6 个参与者、9 条消息、编号有序、且含一次往返（`gw→pay` 回复）。

`examples/realworld/checkout-sequence.ir.json`

## 二、结果

```console
$ execute --spec '{"layout":"layered","palette":"enterprise","baseSize":12}'
  status=succeeded  score=92
  label.overlaps-label (1)
    '2 创建订单' 与 '8 返回结果' 重叠
```

首轮 86 分，有一处 `note` 压节点（**我给的坐标不当**）；调整后 92 分。

## 三、渲染暴露的三个问题

### 1. 标签重叠（检测到）

`s2`（创建订单）与 `s8`（返回结果）方向相反、端点相同，**中点必然重合**。
`text.overlaps-label` 已报告，`SpreadLabels` 未消除——因为它只在位置数下降时才移动，
而这两条的标签无论怎么移都会碰。

### 2. 圆形节点过大（检测未覆盖）

```
user/web  1.85 x 1.85   面积 3.42
order/pay 1.30 x 0.55   面积 0.72     -> 面积差 4.8 倍
```

渲染图上圆形比矩形大三倍，比例失衡。

**几何上无法避免**：圆形内接正方形边长 = 直径 × 0.707，
要容纳 1.30" 宽的文本，直径必须是 `1.30 / 0.70 = 1.86`。

C5（padding 比例化）已把 padding 从 0.60" 降到约 0.26"，但**没有改变这条几何约束**。

**唯一出路是让圆内文本换行**：两行 0.65" 宽的文本只需要 0.93" 直径。这是设计决策——
圆形在时序图中通常表示参与者，短标签（"用户"、"前端"）本可以两行排。

### 3. 连线长距离斜穿（检测未覆盖）

`订单服务 → 消息队列` 斜穿页面中央，因为 Layered 把 `mq` 排到 `order` 上方两层。

时序图本应按**时间顺序**横向或纵向排列消息，而 Layered 按图深度分层。
`SuggestStrategy` 对 `kind=workflow` 且无容器选 Flow，但 Flow 也按 BFS 序列排，不按消息编号。

## 四、结论

| 方面 | 状态 |
| --- | --- |
| 结构正确性 | ✅ 6 参与者 9 消息全部落位，角色配色正确 |
| 标签可读性 | ⚠️ 1 处重叠（已检测，未消除） |
| 节点比例 | ⚠️ 圆形比矩形大 4.8 倍（几何必然） |
| 流程图形态 | ⚠️ 不按时序排列（Layered/Flow 都不适配方） |

**分数 92，但渲染图作为时序图并不合格。**

## 五、分数与观感的第 N 次背离

这是同一现象的第六次记录：分数衡量几何冲突，**不衡量"这是不是一张可用的时序图"**。

时序图需要"参与者列 + 时间轴"，而引擎只有分层和流式两种排列方式。
**这是表达能力缺口，不是布局参数问题。**

## 六、这一轮的价值

1. 确认引擎在**第五种结构**上仍能产出结构正确的图（92 分）
2. 发现**时序图不在引擎的表达能力内**——它需要专门的布局策略
3. 把 C5 的遗留问题定量：圆形必须 1.86" 才能容纳 1.30" 文本，除非允许换行

## 七、手工摆放的可行性验证（2026-11-18，第二轮）

问题：能否用 `layout=manual` + 手写坐标做出时序图，从而避免新增布局策略？

### 试验

5 个参与者、8 条消息，手工给每个参与者 `anchor: {mode:"fixed", x:…, y:9}`。

### 结果：不能

| 尝试 | 结果 |
| --- | --- |
| `manual` + 默认 `canvas.auto` | 坐标被 recenter 改到 `y=1.5`（见 C23） |
| `manual` + `canvas.fixed` | 坐标保住 `y=9`，但**形态仍不是时序图** |

第二种的渲染图：5 个参与者水平排列、消息挤在同一水平线上、
去程与回程标签完全重叠（「1 提交」与「8 展示」、「3 支付」与「6 完成」）。

### 为什么手工坐标也不够

时序图的三要素：

1. **参与者列**——每个参与者一条垂直线
2. **生命线**——从头部延伸到底部的虚线，消息在生命线上取点
3. **时间轴**——消息按序号自上而下排列

引擎的 `FreePath` 可以画生命线，`anchor` 可以摆头部，
但**消息的起止点必须落在两个参与者的生命线上**，而连线端点是节点边框，
不是"某条竖线上的某个 y"。

也就是说：连线的两个端点由**节点位置**决定，
而时序图需要它们由**（参与者列, 消息序号）**决定。这是模型的表达能力缺口。

### 结论

**时序图需要新的布局策略**，不是手工摆放能绕过的问题。
实现它需要：`IrEdge` 携带"消息序号"、连线端点可指定为"生命线上的 y"、
以及一个两阶段布局（先摆头部，再按序号排消息）。

**不在本次范围。** 已记录在 `docs/capability-boundaries.md`。
