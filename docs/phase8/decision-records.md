# Phase 8.0 架构决策记录（ADR）

格式：每条包含 背景 / 决策 / 替代方案 / 理由 / 后果 / 复核条件。
**复核条件很重要**——它写明什么证据会推翻该决策。

## ADR-001：不做大重构，采用最小演进

**状态：** 提议

**背景**
任务 §5 要求先审计再决定是否重构。审计显示：核心执行路径 54 项能力已验证，
而多数缺口来自依赖库能力未被使用（256 个公开类型只用了 14 个）。

**决策**
不重写分层架构，不新增程序集。只在现有四层内做四处扩展。

**替代方案**
1. 重写为"通用 Shape 树"（任务 §4.1 字面理解）——**否决**
2. 引入 Graphviz/MSAGL 替换布局——**否决**（Phase 0 已论证）
3. 全量迁移到直接操作 OPC，抛弃 OfficeIMO——**否决**

**理由**
- 重写会丢弃 54 项已验证能力，且不能解决实际缺陷（缺陷是局部的）
- 通用 Shape 树会诱导"万能对象"，任务 §4.1 自己就禁止
- OfficeIMO 提供了资产/母版/Callout 等大量未用能力，抛弃等于自建这些

**后果**
- 优点：风险低，每一步可独立验收
- 缺点：`Node/TextBlock/FreePath` 并列而非统一继承，调用方需按类型分支

**复核条件**
若 Phase 8.4 的"区域协调"证明并列集合无法表达真实构图需求
（例如需要跨类型统一 Z-order 与变换），则应重新考虑引入轻量基类。

## ADR-002：新增对象用并列集合，不引入通用 Shape 基类

**状态：** 提议

**背景**
任务 §4.1 要求"不能把已有语义对象退化成普通 Shape"，同时"不能设计无限膨胀的万能对象"。

**决策**
`Page` 增加 `TextBlocks` / `Paths` 并列集合；不引入 `abstract Shape`。

**替代方案**
1. `abstract Shape` + Node/TextBlock/FreePath 继承——**否决**
2. 全部塞进 `Node`，用 `Node.Type` 区分——**否决**
3. 单一 `List<object>` 万能集合——**否决**

**理由**
- 继承会让布局器被迫接受"任意 Shape"，而布局只对 Node 有意义
- 塞进 Node 会让 `Node.GroupId`/`Edge.From` 等语义字段对文本/路径无意义
- 并列集合让每类对象只进入该出现的算法，类型系统直接挡住误用

**后果**
- 优点：算法签名清晰（`Layout(Page)` 只动 `Nodes`）
- 缺点：Z-order 跨集合需靠 `Page.ShapeOrder`（id 全序列表）统一，序列化是四个数组

**复核条件**
若出现"文本必须参与节点布局"的真实需求（如自动图例排布），
则应提供组合而非继承：`Node.TextBlockId` 引用，而非让 TextBlock 变成 Node。

## ADR-002b：Z-order 用 id 全序列表，不用单一标量

**状态：** 提议（已按负责人意见修正初稿）

**背景**
`Page.ShapeOrder` 已存在（`DiagramModel.cs:56`），Reader 写入、Writer 从不消费，
导致每次保存丢失 Z-order。初稿提议改为 `Page.ZOrderHint`（`int?`）。

**决策**
保留并**强化** `Page.ShapeOrder: List<string>?`：
Reader 必须保留 XML 中 `<Shape>` 的真实出现顺序，Writer 必须按该列表输出。

**替代方案**
1. `int? ZOrderHint` —— **否决**（见下）
2. 每个对象上加 `int Z` 字段 —— 否决（跨集合排序时要重排整数值，易冲突）
3. 引入 `abstract Shape` 基类后统一排序 —— 否决（见 ADR-002）

**拒绝 ZOrderHint 的理由**
Z-order 的本质是**对象间的全序**，不是"页面的一个层次值"。
一个标量无法表达：
- 跨类型交错（Node → TextBlock → Node → FreePath）
- 部分对象参与排序（"其余保持原样"）
- 同一模型重建后顺序稳定

id 列表天然表达全序，且直接对应 XML 中 `<Shape>` 的输出次序。

**后果**
- 优点：与 VSDX 的实际表达方式一一对应；可跨类型排序；可直接 diff
- 缺点：id 必须全局唯一（Node / TextBlock / FreePath / Group 共用命名空间）；
  列表与集合可能不同步，需在 `Normalize` 中校验

**复核条件**
若出现"数千对象、频繁局部重排"的性能问题，可缓存 id→索引 映射；
但**数据结构不变**，不应退回标量方案。

## ADR-003：资产接入 Stencil，不自建资产系统

**状态：** 提议

**背景**
任务 §8.3 要求"建立真正可扩展的原生图形和资产机制"。
审计实测：`ImportMastersAndGet` 返回 5 个母版即可用；
`VisioStencilShape` 已含 `SourceLicense` / `SourceAttribution` / `PreviewImage` /
`SourceConnectionPoints` / `IsSupported`。

**决策**
新增 `StencilCatalog` 包装 `VisioStencilCatalog`；
`AssetResolver.Resolve(semanticId)` 优先原生 master，其次 stencil，最后降级矩形并报告。

**替代方案**
1. 扩展 `MasterCatalog` 硬编码更多形状——**否决**（无法覆盖领域资产）
2. 自建资产格式（JSON + 自有 schema）——**否决**（与 Visio 原生 stencil 不兼容）
3. 直接内嵌 SVG 到每个节点——**否决**（依赖未验证的图片能力）

**理由**
- 库已提供，自建是重复劳动
- Visio 原生 stencil 是用户已有的资产形态，兼容性最好
- 许可证/归属字段正好满足任务 §8.3 要求，自建还要重新设计

**后果**
- 优点：接入成本低，复用 Visio 资产生态
- 缺点：依赖 `VisioStencilCatalog` 的稳定性；stencil 加载失败需降级路径

**复核条件**
若 `VisioStencilCatalog.Load` 对真实 Visio stencil 文件（.vssx）失败，
则降级为"仅支持从已有 VSDX 导入母版"（`ImportMasters` 已实测可用）。

## ADR-004：图片/SVG 已完成实验，8.3 直接进入实现

**状态：** 已修订（原为"先实验后承诺"，实验已完成）

**背景**
初稿决策是"Phase 8.3 的第一项任务是技术实验，不是实现"。
该实验已在 Phase 8.0 完成，结论明确。

> **修订说明：** 本 ADR 原文写的是"实验待做，若失败则标记 🚫"。
> 实验已做完且通过，原文已过时。8.3 不再需要重复实验。

**实验结论（Phase 8.0 实测，见 `technical-experiments.md`）**

| 项 | 结论 | 关键细节 |
| --- | --- | --- |
| 自由路径 | ✅ 包格式可行 | 4 段折线写入、渲染、往返保留均成功 |
| 图片 | ✅ 包格式可行 | `ForeignData` + media + rel；校验 VALID；`png/jpg/emf` Content-Type 库已写 |
| SVG | ✅ 包格式可行 | 需手工补 `image/svg+xml` Content-Type |

**但"格式可行"≠"产品可用"**，三项在 Engine 里都是零支持（见能力矩阵 `🔬 LAB`）。

**决策**
8.3 直接进入实现，不再做可行性实验。实现范围：

1. 媒体写入器（`visio/media/*` + 关系 + Content-Type 补全）
2. 模型字段（`ImageAsset` / `SvgAsset`）
3. **Renderer 必须显示真实图片**——占位框只允许是 8.1–8.2 的阶段性限制，
   **不接受作为 8.3 的验收结果**（负责人明确要求）
4. 图片替换（增量编辑已存在的图片）
5. SVG 独立验证

**替代方案**
1. 继续用占位框验收 —— **明确否决**（负责人意见 3）
2. 用 SVG 形状模拟图片 —— 否决（不是真图片，不可替换）

**后果**
- 优点：可行性已确定，8.3 可估算工期
- 缺点：Renderer 显示真实位图可能需要引入图像解码依赖（如 SkiaSharp 或 ImageSharp），
  这是 8.3 需要单独评估的新依赖

**复核条件**
若 Renderer 无法在不引入重型依赖的前提下显示真实位图，
需向负责人报告并决定：引入依赖，或把"Renderer 显示"降级为"仅 Visio 中可见"。

## ADR-005：区域复用 Group.AutoSize=false，不新增 FixedSize、不引入 Coordinator

**状态：** 提议

**背景**
任务 §4.4 要求多区域构图协调，§9 又警告"不能让 Coordinator 变成强制统一构图的系统"。

**决策（已修正初稿）**
**不新增 `FixedSize`**——`Group.AutoSize: bool?` 已经实现同等语义
（`DiagramLayout.cs:33` 在 `AutoSize == false` 时跳过反算、保留 Bounds）。
只新增 `Group.LayoutStrategy`，并明确 `DesignSpec.ContainerLayouts` 是它的输入通道。

**替代方案**
1. 独立 `CompositionCoordinator` 项目——**否决**（职责与布局器重叠）
2. 新增 `Region` 类型——**否决**（与 Group 语义重复）
3. 新增 `FixedSize` 字段——**否决**（与 AutoSize 语义重复，已实测确认）
4. 完全交给 Figure Agent 算好坐标——**否决**（违反职责边界）

**理由**
- Group 已经是"区域"的载体，只缺"尺寸由上层决定"这个开关
- 独立协调器立刻面临"谁说了算"问题，与布局器冲突
- 复用已验证的 `LocalRelayout`，风险低

**后果**
- 优点：零新概念，复用现有机制
- 缺点：区域嵌套时的空间分配仍是简单堆叠，复杂构图可能不够

**复核条件**
若真实案例需要"区域间按比例分配剩余空间"或"区域自适应内容但受上限约束"，
则需引入区域求解器（约束布局），此时 Group 上的两个字段不够用。

## ADR-006：保真检测独立于几何检测

**状态：** 提议

**背景**
审计发现的 P0 缺陷（外部无几何形状被注入矩形）在 283 项测试全绿时仍存在。
原因：所有检查都只看"几何是否合法"，没有"结构是否被改动"。

**决策**
新增 `check-fidelity`：比对修改前后的 VSDX 结构（shape 数、cell 集合、
Geometry 段数、关系数、媒体文件），输出 lost/added/modified。

**替代方案**
1. 只加单元测试覆盖该场景——**否决**（只能覆盖已知场景）
2. 在写入器里加断言——**否决**（无法知道"原始应该是什么"）

**理由**
- 结构比对对**任意**外部文件都成立，不依赖预先枚举场景
- 能把"未映射对象是否被破坏"从人工判断变成可复核输出

**后果**
- 优点：同类保真问题第一次出现就能被发现
- 缺点：需要保存"修改前"快照；比对规则需定义"什么是可接受的差异"（如 XML 格式化）

**复核条件**
若差异报告过于嘈杂（例如每次都有大量无害差异），
应引入白名单（已知无损差异）而非放弃检测。

## ADR-007：L4 未验证不得由其它层级替代

**状态：** 接受（沿用 Phase 7）

**背景**
任务多处要求 L4 Visio 原生验收，当前无 Windows + Visio 环境。

**决策**
在所有报告中如实标注 L4 未验证。**不得**用 L1（包结构）、L2（后端重载）、
L3（第三方渲染）的结果推断 L4 通过。

**替代方案**
1. 用渲染结果近似 Visio 行为——**否决**（渲染器是独立实现）
2. 用 OPC 结构正确推断"Visio 一定能打开"——**否决**（结构正确是必要条件，非充分条件）

**理由**
Phase 7 已确立此原则。Phase 8 要新增图片/SVG/自定义路径，
这些恰恰是 L1–L3 最难保证、L4 最容易暴露问题的特性。

**后果**
- 优点：不产生虚假信心
- 缺点：项目在"可编辑"这一点上始终有一块未闭合风险

**复核条件**
一旦具备 Windows + Visio 环境，应立即补做，并优先验证 Phase 8 新增的对象类型。
