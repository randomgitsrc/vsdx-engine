# 状态报告

**用途**：回答「这个项目现在处在什么位置」。
**数字**一律用命令查，不写进本文——它们会变，而这份文件不会跟着变。

```bash
git rev-list --count HEAD
find src -name "*.cs" | xargs cat | wc -l
dotnet test VsdxEngine.sln -c Release        # 全部通过，0 warning
grep -cE '^## [0-9]+\.' docs/phase8/known-issues.md   # 未解项
```

---

## 一、它是什么

一个**不依赖 Visio** 的引擎：创建、读取、增量修改、渲染真实的 `.vsdx`。
驱动的入口是三层协议——`DiagramIr`（内容）→ `DesignSpec`（外观）→ `ExecutionResult`（结果）——
设计目的是让 Agent 能构图、能修改、能从结果判断自己做得对不对。

## 二、验证到了哪一步

| 层级 | 手段 | 状态 |
| --- | --- | --- |
| L1 包结构 | 18 项 OPC / Visio 语义检查（`validate --json` 的 `checks`）| ✅ |
| L2 读回 | 往返保真，对象 id 稳定 | ✅ |
| L3 渲染 | PNG / SVG 内容一致 | ✅ |
| **L4 Visio 原生** | 真实 Visio 打开并编辑 | ⬜ **从未执行** |

**L1–L3 不能替代 L4。** 项目定义的核心承诺是「原生、可编辑的 VSDX」，
这一条**目前是假设，不是结论**——它是唯一需要外部条件（一台装有 Visio 的 Windows 机器）的项。

## 三、能画什么

| 场景 | 分数 | 说明 |
| --- | --- | --- |
| `cbo` 跨境电商架构 | 98 | 3 层容器；矩形客户端使内容右移 |
| `user-data-flow` 用户数据流 | 100 | 无容器长链 |
| `netflix-active-active` Netflix 双活 | 94 | 2 区域 + 跨区复制；**唯一外部来源案例**（见 `examples/realworld/netflix-active-active.md`）|
| `order-swimlane` 订单泳道 | 100 | 3 泳道按 `order` |
| `org-tree` 组织架构 | 100 | 3 层树 |
| `deploy-topology` 部署拓扑 | 96 | 少量连线交叉，**拓扑性**，非缺陷（§八 of `capability-boundaries.md`）|
| `checkout-sequence` 下单时序 | 88 | 结构对但非时序形态 |

六个场景**全部通过硬约束**。18 个基准同样全部通过。

分数用 `check-layout` 实测；**它会随修复变化**，以命令为准。

## 四、不能画好的

- **时序图**：模型层无消息序号与生命线寻址
- **状态机**：无状态语义（入口/出口/复合）
- **精确对齐的图**：布局是推导的，不是手工钉的
- **需要图例避让连线标签**：标签在渲染时绘制，不在任何包围盒里

详见 `capability-boundaries.md`。

## 六、这个项目的可信度来自哪里

不是测试数量，是这三件事：

1. **报告而不静默**。做不到的请求进 `unmetConstraints`，做了的进 `appliedDesignNotes`。
   这条铁律在 IR→模型→产物→报告四层各找到过实例，都已修并固定。
2. **检测器不是空的**。24 类检测每一项都被观测到触发过，关键项测了边界与反证。
3. **文档与代码由测试绑定**。改能力、数字、命令时对应测试会失败——那是设计。

## 七、一条必须记住的经验

**约束检测通过 ≠ 图纸专业。**

`cbo` 曾以 98 分通过全部几何检查，而「数据层 Data」标题被节点压住——只有渲染成图片并打开看才发现。
`checkout-sequence` 报利用率 84%，实际节点只占 23%，图上约 70% 是空白。

**判断一张图能不能用，必须看图，不能只看分数。**
