## 三、重大发现：基准的 18/18 依赖特定参数

```console
$ create --input benchmarks/architecture/complex.json --output b3.vsdx
$ check-layout b3.vsdx
  score=0/100
  group.overlap (1)
    [error] 容器 'grp_svc' 与 'grp_acc' 重叠 10.85" × 0.11"

$ create --input benchmarks/architecture/complex.json --output b2.vsdx \
    --layout auto --fit-text --fit-page --recenter
$ check-layout b2.vsdx
  score=100/100
```

**同一份基准模型，不带参数 0 分，带参数 100 分。**

这不是缺陷，但意味着：

1. **"18/18 基准通过"只在特定参数组合下成立**，回验时不可省略参数
2. 新用户按 Skill 直接 `create`（不带参数）会得到重叠的产出
3. `skill/SKILL.md` §4 确实提到了这些参数，但**不是默认行为**

**建议：** `create` 应在容器重叠时自动修正或显式警告，
而不是依赖调用方记得加四个参数。

## 四、新缺陷 C3 的发现过程

v2–v6 全部 0 分时，我先怀疑自己的设计，逐一改写布局（4 个版本），
但问题稳定复现。导出 waypoints 后才定位到路由：

```
e10: pay(5.40,7.70)   -> redis(5.40,2.50)    waypoints=[(1.10,6.99),(1.10,3.26)]
e11: customs(8.20,7.70)-> es(8.20,2.50)      waypoints=[(1.10,6.99),(1.10,3.26)]
e12: stock(11.00,7.70)-> s3(11.00,2.50)      waypoints=[(15.30,6.99),(15.30,3.26)]
```

**起止 x 完全相同，通道却是 1.10 / 15.30 —— 页面的首尾两个通道。**

根因在 `OrthogonalRouter.ComputeChannels`：它只生成**列与列之间**的通道。
两点同列时，它们之间没有列间隙，遍历结果只能落在最外侧。

**反讽之处：** `skill/SKILL.md` §2 第 4 条明确推荐
"Put each data store directly under the service that owns it"（存储放服务正下方）——
**这正是触发该缺陷的布局**。

详见 `docs/phase8/phase8.3-candidates.md` C3。

# 第二轮：修复 15 项缺陷之后（2026-11-18，HEAD `67821aa`）

实测证实了这一点：用修复后的代码重跑第一轮那张图，**PNG 的 MD5 与旧产物完全相同**
（`e2e1d59aee8b`）。palette、typography、roleColors 这些修复对它没有任何效果，
因为它根本不走 spec。

**这是第一轮报告的一个盲区**：它把"真实制图验证"做在了错误的路径上。

## 二、execute 路径的复测

**修复确实生效**，目视可辨：

| 缺陷 4（typography） | 标题 25pt / 容器 15pt / 节点 14pt，同一字族 |

## 三、但 `score=0`

```console
$ check-layout enterprise.vsdx
  score=0/100
  text.overflow-horizontal (2)
    [error] 'web' 最长行约 0.82" 宽，实际 0.70"
    [error] 'app' 最长行约 0.78" 宽，实际 0.70"
```

**这暴露了一个新缺陷（C4）**：`DiagramSizer` 不区分形状，圆形节点按矩形算文字宽度，
而圆内接矩形的宽度只有直径的约 70%。

```

```

**这不是缺陷 20 引入的回归**，而是它揭露的既有问题——升级前这类图只报 `score` 偏低，
仍判 `hard=true`。缺陷 20 的做法依然正确：裁切不该被当作可交付。

# 第三轮：新场景验证（部署拓扑，2026-11-18，HEAD `55efbb7`）

## 一、为什么换场景

前两轮都用同一张跨境电商架构图。反复优化同一张图会掩盖问题——
引擎在**没见过的结构**上表现如何，才是真实能力的检验。

新增 `examples/realworld/deploy-topology.ir.json`：
生产环境部署拓扑，12 节点 / 14 边 / 3 区 / 2 文本块。
结构上与前一张不同：**一对多扇出**（LB → 3 个 API）、**多对一汇聚**（3 个 API → 主库）、
**跨区直连**（Worker → 从库）。

## 二、结果

```console
$ execute --spec '{"theme":{"palette":"technical"},"typography":{"baseSize":13}}'
  score=94/100
  edge.crossing (5)
  page utilisation 79%
```

**94 分，5 处交叉，利用率 79%。** 前一张图是 95 分 1 处交叉。

新场景表现略差但仍属可用——说明引擎不是只对调优过的那张图有效。

## 三、我的一处目视误判

渲染图上，CDN 节点和 Worker 2 看起来**超出了容器左右边界**。我一度按缺陷处理。

实测后：

```
dmz 容器 [0.55, 7.01]，cdn 节点 [0.85, 2.15]    <- 在内
app 容器 [0.55, 9.85]，wk2 节点 [8.25, 9.55]    <- 在内
```

**几何完全正确，间距都是 0.30"（PaddingX 默认值）。**

看起来"超出"是因为容器边框与节点边框只差 0.30"，在这个渲染尺度上几乎贴合。

**这是我的读图错误，不是产品缺陷。** 记录在此以免后续重复误判。

值得注意：`check-layout` 没有报 containment 问题，**检测器是对的，我的眼睛错了**。

## 四、发现一个真实问题（C13）

图例文字是 IR 里手写的：

```json
{"role":"legend","text":"蓝=入口  绿=应用  橙=数据"}
```

配 `technical` palette 后实际是灰/黄：

```
gateway  #FFC000 (黄)
service  #BFBFBF (灰)
```

**图例说"绿=应用"，实际是灰色。**

根因：图例是纯文本，与 palette 无关联。这不是引擎 bug（它没有"理解图例语义"的能力），
而是**真实使用者会踩的陷阱**：同一 IR 配不同 palette，图例只有一套文字。

要让图例跟随 palette，需要协议支持"图例项绑定角色"，属扩展。

**立即可做的**：Skill/文档提示——换 palette 时同步改图例，或图例用中性表述。

## 五、这一轮的价值

1. **验证了引擎在陌生结构上仍可用**（94 分），不是只对调优样例有效
2. **发现自己一次目视误判**，并纠正——检测器比我的眼睛可靠
3. **发现一个协议表达能力边界**（图例与配色解耦），已登记为 C13

- 仍是架构/部署类图，未测纯数据流、时序图
- 未在 Visio 中验证（L4）

# 第四轮：纯流式结构（数据流图，2026-11-18，HEAD `1512cb5`）

## 一、换第三种结构

前两轮都是**分层**结构（3 个容器）。这一轮换成**无容器**的纯数据流：
12 节点 / 12 边 / 0 容器，且是一对多扇出后多对一汇聚的形态。

新增 `examples/realworld/user-data-flow.ir.json`。

## 二、结果：分数很高，观感很差

```console
$ execute --spec '{"layout":"auto"}'      # 默认 Layered
  score=98/100   交叉 1   利用率 86%
```

**但渲染图是这样的**：

```
页面 11.00 x 23.30   宽高比 1:2.1
节点 x 范围 [0.84, 5.10]   <- 只占 4.26"
标题 x=6.95 范围[3.45,10.45]
```

**节点排成一条竖线，右侧三分之二是空白，标题浮在空白处。**

## 三、根因（C14）

**1. Layered 引擎不折行。** `MaxNodesPerRow` 只被 `GridLayoutEngine` 使用，
Layered 把同一 band 的节点无限排成一列。

**2. 页面宽度由标题决定。** 节点只到 x=5.10，标题撑到 10.45，页面因此宽 11"。
`ClampDecorationsToPage` 只保证不出页面，不保证与内容协调。

**3. 利用率公式掩盖了问题。** 它用**内容包围盒**算——标题把包围盒撑宽，
所以 86% 看起来正常。**分数无法反映"内容排成一条线、其余空白"**。

## 四、对照实验：换 grid 布局

```console
$ execute --spec '{"layout":"grid"}'
  score=95/100   交叉 1
  页面 14.95 x 8.50   宽高比 1:0.6      <- 接近 16:9
```

**形态明显更好**：两行排列、标题居中、宽高比合理。

**但分数更低（95 vs 98）。** 又一次印证：**分数高不等于观感好**。

代价是 `grid` 不尊重链路：ETL 清洗在右上、维度补全在左下，中间靠长线连接。

产物：`user-data-flow-layered.png`（98 分，竖列）与 `user-data-flow-grid.png`（95 分，两行）。

## 五、三个场景的横向对比

| 场景 | 结构 | 分数 | 观感 |
| --- | --- | --- | --- |
| 跨境电商架构 | 3 层容器 | 95 | 好 |
| 部署拓扑 | 3 层容器 | 94 | 好 |
| **数据流** | **无容器** | **98** | **差（竖列）** |

**分数最高的场景观感最差。**

结论：**引擎在分层结构上表现好，在无容器流式结构上退化**。
这不是某个缺陷，而是布局策略的适用范围问题。

- 未测时序图（按时间轴）
- 未在 Visio 中验证

## 目视复核（2026-11-18）

四个参考场景全部渲染成 PNG 并**实际打开查看**。这一步此前从未做过——只跑检测器不看图，
漏掉了检测器看不到的问题。

| 场景 | 分数 | 目视发现 |
| --- | --- | --- |
| 跨境电商架构 | 86 | 8 处容器标题被首行成员压住（已加 `container.heading-collision` 检测） |
| 部署拓扑 | 82 | 11 处同类问题；另有 40% 上边距（已修：内容未居中于纸张） |
| 用户数据流 | 100 | **未发现缺陷** |
| 下单时序 | 88 | 结构对但非时序形态（已知限制） |

### 一次判断修正：用户数据流的空白

初看渲染图觉得"上下各 40% 空白"，实测：

```
内容 x[0.55,14.78] y[0.55,9.90]
页面 15.57 x 10.45
利用率 82%，上下边距各 0.55"
```

**检测器是对的，我看错了。** 视觉上的稀疏来自 `note` 在底部、标题在顶部、中间是节点区，
而不是真的有空白。

### 圆形节点尺寸

`actor` 角色用圆形，直径 `1.85"`，是矩形节点 `1.30 x 0.55` 的 4.75 倍面积。

**这是正确的**：圆的内接矩形只有直径的 70.7%，要让「Web 埋点」这样的文字放得下，
直径必须是 `1.30 / 0.707 ≈ 1.84`。垂直方向确实浪费，但用椭圆替代圆不符合 `actor` 的惯例。

### 结论

检测器覆盖了 23 类几何问题，**看不到渲染层面的问题**——标题被遮挡就是例子。
`container.heading-collision` 是针对这类盲区新增的第一项，只检查模型几何，
不检查渲染时绘制的连线标签。

## 补充：两种此前无示例的布局（2026-11-19）

`swimlane` 与 `tree` 从未用于任何真实示例——六种策略里只有四种有产出。补齐后：

| 场景 | 策略 | 分数 | 目视结论 |
| --- | --- | --- | --- |
| `order-swimlane` | swimlane | 88 | 三条泳道按 `order` 排列正确，节点在各自泳道内；**连线为斜线**，跨泳道时不够专业 |
| `org-tree` | tree | 100 | 三层结构清晰、节点尺寸统一；无几何问题 |

### 一次 IR 写错

`org-tree` 首版把 `CTO` 设成 `role: actor`，得到直径 1.85" 的圆形，占画面近三分之一。
**这不是引擎问题**——`actor` 用圆形是设计（内接矩形只有直径的 70.7%），
而 CTO 是组织节点不是执行者。改成 `service` 后 100 分且视觉正常。

### swimlane 的连线是斜线

跨泳道的连线走直线而非正交折线，视觉上像手绘。`OrthogonalRouter` 在容器内的路径
未强制正交——这与 `capability-boundaries.md` 里「不保证正交路由」一致，属已知限制。
