## D-4：TextBlock 字体是否需要可回读 —— ✅ 已由任务书裁定为方案 A

**本项已由任务书 §3.5 与 §4.4 夹定，不再是待决问题。**

> §3.5：「**Reader 能正确读回已支持的样式**」「无法表达或渲染的样式**必须报告**」
> §4.4：「不为了视觉系统**重写** Writer / Reader」——补一处字体注册不属于重写

**裁决：方案 A —— 修 `VisioTextBlockBridge`，让字体注册进 `FaceNames`。**

选 B（声明不回读）会触发 §3.5 的"必须报告"：每次遇到 TextBlock 自定义字体
都要进 `unmetConstraints`，比修好更啰嗦，且调用方每次都要处理同一个已知退化。

**技术事实（实测）：**

| | Node（`fontFamily: Georgia`） | TextBlock（`font: Verdana`） |
| --- | --- | --- |
| `FaceNames` 条目 | 3 | 0 |
| 字体名在 `document.xml` | ✅ | ❌ |
| `Character` 段 | ✅ | ❌ |
| Reader 能读回 | ✅ | ❌ |

**不是同一个 bug**：Node 走库的 `TextStyle` 自动注册，TextBlock 因 Bridge 在
保存后才补写 XML 而绕过该机制。

**修法（推荐 A1）：** TextBlock 改用库的 `VisioTextStyle.FontFamily`，
与 Node 共用同一条已验证路径。避免两套字体机制长期并存——
这正是本审计反复出现的缺陷模式（同一能力两条路径、行为不一致）。

## D-18：缺陷 18（Renderer 不消费 FontFamily）如何处置

**状态：** ⬜ **待负责人裁决**（本轮唯一未决项）

### 事实

三种字体（含一个不存在的）渲染出的 PNG **MD5 完全相同**。根因是
`OfficeImoVsdxRenderer.cs:37` 只把 `request.FontFile` 传给 `Resolve`，
从不读 VSDX 里的 `FontFamily`。

### 两个选项

| 选项 | 做法 | 后果 |
| --- | --- | --- |
| **A. 修渲染器** | 从 VSDX 读 `FaceName` → 映射字体文件 → 传入 `Resolve` | 字体在预览中生效；T2d 工时"中"；管线已通（`Resolve` 本就支持 `preferredFontFile`） |
| **B. 声明限制** | 不改渲染器；T2c 白名单把 `font-family` 标为"仅 VSDX 内有效，预览不体现" | 零工时；但**预览与交付物不一致**，违反任务书 §3.5"Renderer 不得制造与 VSDX 不一致的预览" |

### 我的建议

**选 A，但可以分步。**

理由：

1. 任务书 §3.5 明文禁止"Renderer 制造与 VSDX 不一致的预览"。选 B 直接违反该条。
2. 修复路径已查明且**不需要架构改动**——`FontResolver.Resolve` 已有
   `preferredFontFile` 参数，缺的是上游传值。
3. 这与本审计反复出现的模式一致（缺陷 15/18/19 都是"管线在、最后一跳断"）：
   补一跳比长期维持不一致更省事。

**若选 B**，必须在 `ExecutionResult` 里**每次**报告
"字体族未在预览中体现"（`style.renderer-partial`），
且能力矩阵中 `font-family` 标为 ⚠️ 而非 ✅。不能只是文档里写一句。

**折中方案（可选）：** 先做 B 的声明，把 A 放在 8.3 与图片渲染一起做
（两者都要碰渲染器，合并做更省）。但需你确认接受这段期间的不一致。
