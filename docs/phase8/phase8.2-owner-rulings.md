## D-4 — TextBlock 字体回读

**状态：** ✅ **已由任务书 §3.5 与 §4.4 裁定为方案 A**

我上一轮把它作为"待裁决"上报，但它其实被任务书两条要求夹定了：

**任务书 §3.5（第 281 行）明确要求：**

> - 样式最终写入真实 VSDX；
> - **Reader 能正确读回已支持的样式；**
> - 保存后的 VSDX 再次渲染，样式没有丢失；
> - **无法表达或渲染的样式必须报告。**

**任务书 §4.4 的限制范围：**

> 4. 不为了视觉系统**重写**现有 VSDX Writer / Reader。

**两条合起来：**

| 约束 | 含义 |
| --- | --- |
| §3.5「Reader 能正确读回」 | TextBlock 字体要么能读回，要么必须**报告**为无法表达 |
| §4.4 禁止「重写」 | 但修一处字体注册**不是重写**，是补一个缺失的注册 |

**因此方案 B（声明"不回读"）需要额外满足 §3.5 的"必须报告"**——
即每次遇到 TextBlock 自定义字体都要进 `unmetConstraints`。
那比修好它更啰嗦，且调用方每次都要处理同一个已知退化。

**裁决：方案 A —— 修 `VisioTextBlockBridge`，让字体注册进 `FaceNames`。**

**修法（两条路径，选其一）：**

| 路径 | 做法 | 影响 |
| --- | --- | --- |
| A1 | TextBlock 改用库的 `VisioTextStyle.FontFamily`，在**保存前**创建 | 改动较大，但走与 Node 相同的已验证路径 |
| A2 | 保存后补 `<FaceName>` 并让 `Font` cell 用索引引用 | 改动局部，但需正确维护 `document.xml` 的索引 |

**推荐 A1**：与 Node 共用同一条路径，避免两套字体机制长期并存——
这正是本审计反复出现的缺陷模式（同一个能力两条路径、行为不一致）。

**T2 工时：中。** 不是因为复杂，而是因为要真正验证"写入 → 注册 → 读回"整条链，
而不是再一次"写进去就算完成"。

## D-18 — Renderer 字体支持

**状态：** ✅ **已由任务书 §3.5 裁定为方案 A**

我上一轮把它作为"唯一未决项"上报。**它其实早被任务书定死了**：

> **§3.5 VSDX 与 Renderer 一致**
> 必须保证：
> - 样式最终写入真实 VSDX；
> - Reader 能正确读回已支持的样式；
> - **保存后的 VSDX 再次渲染，样式没有丢失；**
> - **`Renderer` 不得通过另一套独立规则制造与 VSDX 不一致的预览；**
> - 无法表达或渲染的样式必须报告。
> - Renderer 的输入仍应是最终保存的 VSDX，而不是直接使用内存模型另外绘制一张图。

**当前实现直接违反第 4 条：**

```csharp
// OfficeImoVsdxRenderer.cs:37
var fontFile = resolver.Resolve(requiresCjk, request.FontFile);
//                                        ^^^^^^^^^^^^^^^^ 只来自请求
```

`FontResolver` 内部按"是否 CJK"二选一挑字体文件（`FontResolver.cs:52-70`），
**从不读取 VSDX 里的 `FontFamily`**——这正是"另一套独立规则"。

实测三种字体（含一个不存在的）产出 PNG 的 MD5 **完全相同**，
证明预览与 VSDX 内容无关。

**裁决：方案 A —— 修渲染器，让字体来自 VSDX。**

| 步 | 改动 |
| --- | --- |
| 1 | 从 `document.xml` 的 `FaceNames` 收集实际使用的字体名 |
| 2 | 新增 `FontResolver.ResolveByFamilyName(string family)` 映射到系统字体文件 |
| 3 | 传入 `Resolve` 的 `preferredFontFile`；找不到时**降级并进 `unmet`** |

**`Resolve` 已支持 `preferredFontFile` 参数**，所以这不是架构改动，是补最后一跳。

**方案 B（声明"字体仅 Visio 内生效"）被排除**——它正是 §3.5 第 4 条禁止的情况。
